## 100 用户 / 1000 来源合成负载

Windows 11、Python 3.14.3、PostgreSQL 18.6，本机报告 32 个逻辑处理器。4 个独立网站进程，每进程 8 个线程；采集与网站分离。初始化 10,000 条历史通知，100 个登录用户每秒读取一次页面。来源配比为 80% 静态、10% 动态、10% 持续拒绝；传输延迟与浏览器回复采用确定性模拟，任务领取、延期、解析、数据库与页面读取是真实执行。

240 秒结果：

- 24,000 次阅读请求，0 个请求错误，P95 **604.64ms**。
- 900 个有效来源完成；100 个模拟拒绝来源标记失败，没有假报空列表成功。
- 待执行与运行中的任务均归零；新增 900 条通知，10,000 条历史通知全部保留。
- 排队等待 P95 **154.27 秒**，worker 未出现未处理异常。

原始报告：`data/source-audits/capacity-pg-final-20260924.json`。此前将网站与采集放在同一 Python 进程的诊断负载未达到响应目标；部署将进程分离，容量基准配置可扩展网站实例，不能仅靠增加线程。

**这不是指定 8 核 16GB 服务器的容量验收。** 未测真实浏览器内存、官网延迟和连续两个 30 分钟周期；不能用本机合成结果承诺 1000 个任意动态来源都能按期完成。`scripts/acceptance_load.py --url ...` 可对已部署隔离环境做实际 HTTP 压测，同时应采集管理员运行指标和容器内存。
