# School Watcher UX 重构规格

日期：2026-09-02  
状态：待最终确认

## 1. 背景与目标

现有界面以学校卡片、玻璃拟态容器和多级菜单组织内容，通知本身不是视觉与交互焦点；普通读者与管理员又共享相似的信息结构，造成导航复杂、任务边界不清。

本次重构采用“统一通知收件箱 + 独立系统管理页面”。普通读者和管理员同等重要，但个人任务与系统级任务不混在同一页面中。首页首先服务通知阅读；个人中心只管理当前用户自己的账户与订阅；系统管理通过管理员专属入口进入。

## 2. 信息架构

### 2.1 通知收件箱

桌面由三个稳定区域组成：

1. 左侧来源筛选：先选学校，再显示该校的发布部门。
2. 中间通知列表：按时间倒序、按日期分段。
3. 右侧详情预览：标题、来源、时间、AI 摘要、正文与原文链接。

打开通知不会离开收件箱，因此保留滚动位置、已选来源和时间条件。直接访问通知链接时，仍可展示独立详情视图。

### 2.2 系统管理页面

系统管理使用独立地址与独立页面结构，不作为通知收件箱内的标签页、抽屉或“阅读 / 管理”模式。建议沿用现有 `/admin` 地址，并为后台使用独立页面框架。

管理导航收敛为：

- 概览
- 学校及其部门
- 抓取任务
- 选择器健康
- 用户
- 平台设置

概览只展示系统健康、需要处理的异常和最近任务，不重复放置所有配置入口。长时间抓取任务提供持续可见的进度与结果。

系统管理不承载个人资料、个人密码、个人密保或个人订阅。后台顶部提供“返回通知”入口，避免使用浏览器后退作为唯一退出方式。

### 2.3 个人中心

个人中心属于所有已登录用户，继续处理当前用户自己的密码、密保和学校订阅。管理员也通过相同个人中心管理自己的账户，但管理员身份不会让系统级功能混入个人页面。

通知页的用户菜单始终可以包含“个人中心”；只有当前用户为管理员时，额外显示“系统管理”。不使用面向所有用户的管理模式切换。

### 2.4 权限边界

- 未登录用户访问系统管理页面时跳转登录。
- 已登录的普通用户直接访问系统管理地址时返回无权限页面，不渲染后台内容。
- 系统管理页面、`/api/admin/*` 以及学校配置、抓取、选择器和用户角色等管理接口都必须由服务端验证管理员角色。
- 隐藏“系统管理”入口只用于减少界面干扰，不作为安全措施。
- 用户被取消管理员角色后，下一次管理页面或接口请求立即失去权限。

项目现有 `User.role`、`User.is_admin` 与 `admin_required` 已具备这一权限基础，实施时继续复用并补齐页面框架与入口隔离。

## 3. 筛选模型

### 3.1 来源

- 部门不是跨学校共享的分类。每个部门只隶属于一所学校，关系固定为“学校 → 该校发布部门 → 通知”。
- 学校为单选控件，包含“全部学校”和每一所已订阅学校。
- 选中具体学校后，下方部门区域只显示这所学校的真实发布部门。部门名称直接显示“教务处”“学生工作部”等，不添加学校前缀。
- 部门可在当前学校范围内多选；同一学校内选择多个部门时采用“或”。
- 切换学校后，自动清空上一所学校的部门选择并载入新学校的部门，避免把无效选择带入另一所学校。
- 选择“全部学校”时，部门区域隐藏或显示不可操作提示“选择一所学校后可按部门筛选”，通知列表显示所有学校。
- 筛选状态同时保留学校标识与部门标识；后端校验被选部门必须隶属于当前学校。

### 3.2 时间

时间控制包含：

- 全部时间
- 近一周
- 年份
- 年份 + 月份

“近一周”与年月选择互斥。选中近一周时停用年月；选择年份或月份时退出近一周。月份必须依附于年份，不提供含义模糊的跨年“某月”。

### 3.3 组合逻辑

来源、时间、阅读状态之间采用“且”。例如：

> 中国石油大学 + 教务处或学生工作部 + 2026 年 9 月 + 未读

筛选栏显示匹配数量。无结果时说明是哪些条件造成空结果，并提供“清除筛选”。筛选写入 URL 查询参数或等价持久状态，使刷新、返回和分享后仍能恢复。

## 4. 阅读交互

- 默认显示全部订阅学校的通知，最新在前。
- 通知行优先展示标题，其次是学校、部门、时间和最多两行摘要。
- 未读使用蓝色时间节点、轻量背景差异与字重共同表达，不只依赖颜色。
- 打开通知后标记为已读，并提供短时“撤销”。
- 上下方向键移动列表焦点，Enter 打开，Esc 在窄屏关闭详情抽屉。
- 详情中的 AI 摘要明确标注，原文链接始终可用。
- 加载、错误、空列表、无筛选结果和内容缺失都有独立状态与明确下一步。

## 5. 响应式行为

- `>= 1200px`：完整三栏。
- `768–1199px`：来源筛选进入可保持状态的侧边面板，列表与详情双栏。
- `< 768px`：单栏列表；筛选使用底部面板，详情作为下一层页面或全屏抽屉。返回后恢复列表位置。
- 触控目标不小于 44px，键盘焦点清晰，支持减少动态效果。

## 6. 视觉系统

视觉依据见根目录 `DESIGN.md`。核心原则如下：

- 使用中性纸面背景、白色阅读面与单一 Notice Blue 强调色。
- 以排版、留白和细分隔线建立层级，不使用渐变玻璃和大面积阴影。
- 通知列表是主角，不重复使用悬浮卡片。
- 使用“时间脊线”作为与校园通知场景相关的唯一标志性元素。
- 深色模式保留信息密度和对比关系，不改造成霓虹主题。

## 7. 去模板化检查

实施采用两层设计约束：

1. `impeccable` 负责产品界面的信息架构、状态、可访问性和响应式完整性。
2. `frontend-design` 负责从校园通知场景中建立有理由的视觉选择，并在实现前后自我审查。

最终检查借鉴 GitHub `funboy322/avoid-ai-design` 的 dashboard 审查方法：所有视觉决定必须能够解释其任务价值；若删除一个装饰不会损害理解，就删除它。

`design-taste-frontend` 不作为主技能，因为其说明明确排除后台、密集产品界面与管理面板；其中关于移除玻璃拟态和保持一致性的条目仅作参考。

## 8. 实施边界

- 优先复用现有 Flask、Jinja、CSS 和 JavaScript，不因视觉重构引入重型前端框架。
- 保留现有数据来源、登录、阅读状态、AI 摘要和管理能力。
- 允许重组模板、CSS 结构和前端交互；后端只补充组合筛选与持久状态所需的最小接口。
- 不在本轮新增通知推送渠道、跨校部门标准化或复杂个性化推荐。

## 9. 验收标准

- 首页首屏的最大视觉面积属于通知列表与当前通知详情。
- 用户最多一次打开筛选面板即可选择学校、该校一个或多个发布部门、时间和阅读状态。
- “近一周”以及指定年月能与任意来源筛选共同工作。
- 普通用户界面不出现系统管理入口，直接访问 `/admin` 或管理接口会被服务端拒绝。
- 管理员从用户菜单进入独立系统管理页面，并能明确返回通知收件箱；个人中心与系统配置不混合。
- 列表、详情、筛选和系统管理页面在浅色与深色模式均可读。
- 不出现渐变玻璃、大 Hero、卡片墙、emoji 图标或无任务意义的装饰。
- 桌面与移动端完成一轮真实内容截图审查，并验证空状态、错误状态和长标题。
