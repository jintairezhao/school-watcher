# 来源整理与爬取引擎评估（2.17）

采集入口、原始官网证据和用户看到的来源层级分别保存。界面复用同一份整理结果：正式目录决定单位层级，实际入口文字决定栏目名称，已验证的单位地址和网站身份连接旧来源与新目录。修复不合并来源记录，不改通知、订阅、已读、收藏或历史正文。

无采集规则、无历史通知且未被明确选择的候选入口留在后台。网站页内局部 CMS 错误和长期没有更新不单独判为来源失败；已有可读取栏目继续使用。旧模板只作为可选的读取线索，规则安装仍须经过列表范围、文章身份和正文验证。

对无网址的正式下属单位，程序检查部门主导航、目标网站标识和返回部门的导航。证据不完整时保留原名和进度，不猜单位隶属，也不要求用户核实。升级修复复用完整缓存，按队列切片继续；新的模型请求仍由原有 Agent 和共同预算控制。

浏览层级与行政隶属分别处理：已确认部门官网的主导航可以证明栏目浏览路径，不强求目标网页提供返回链接。仅有学校首页或友情链接不构成依据；这一类路径不用于补造下属单位关系。栏目标签使用对应区域的真实名称，并保留必要导航上下文。

## 本轮实际验证

- 只读核对克拉玛依校区 166 条存量部门／栏目记录，复现学院拆分、同名占位标签和资助中心错放。
- 保留 43 条公开配置及官网证据作为回放样本；教务部栏目可区分，同学院归为一处，学生资助归入正式下属层级。隔离状态测试验证来源编号、规则、订阅、已读、收藏与正文未改变。
- 同时回归南开大学、山东大学的既有来源发布者样本、电子科技大学真实机构目录以及同名单位、同页多栏、跨校共享域名、过期证据等边界。
- 实际浏览器读取学工、资助、心理咨询、学生管理网站和人大首页；共青团网站一次 45 秒读取未完成，保留为网络／浏览器恢复问题，不以此重写规则。
- 本轮不重新计作“五所高校整校接入／100 条通知”的新验收；未进行新的模型质量对照。来源整理、读取对照和界面检查实际付费模型请求为 0。

## Crawl4AI：底层引擎对照

在独立 Python 3.14 环境安装 Crawl4AI 0.9.4，复用系统 Edge，关闭缓存，不使用模型提取策略。两种浏览器引擎读取相同公开页面：

| 页面 | 现有浏览器 | Crawl4AI | 实际链接数 |
| --- | --- | --- | --- |
| 学工部门首页 | HTTP 200，29.620 秒 | HTTP 200，25.541 秒 | 均为 52 |
| 学生资助首页 | HTTP 200，16.785 秒 | HTTP 200，32.809 秒 | 均为 99 |
| 人大首页 | HTTP 200，10.096 秒 | HTTP 200，7.560 秒 | 均为 444 |

这是小样本非同步读取，包含网站和加载波动，不能据此宣称普遍速度或覆盖率提升。另一次无效目录地址返回 HTTP 404 时，Crawl4AI 的 `success` 仍为真；该地址未计入有效页面比较，应用必须继续检查 HTTP 状态与真实内容。

独立环境共有 97 个发行依赖，`site-packages` 文件共 693,303,838 字节（693.304 MB／661.186 MiB），未包含浏览器或本地大模型。该数值是解压后依赖体积，不是 setup.exe 大小；完整替换后的冻结兼容性、安装包大小、运行内存及复杂异步网站收益尚未验证。

结论：Crawl4AI 作为底层爬取引擎具备可行性，但目前没有实测依据支持整体替换。保留现有统一采集接口和浏览器读取，后续可把它作为按需加载的读取适配器继续验证，验证时须接入既有 URL 安全、共享限速、状态分类、缓存、任务恢复和 API 预算，不把其“成功”标记直接当作接通。

AIHOT 可借鉴的是采集、整理、公开读取的分层和付费请求记录机制；它不直接提供高校机构归属。项目已有持久任务和费用记录，复用有效部分即可。本轮未复制其代码或引入 Node／数据库框架。
